# AutoBe Codebase Analysis

## 1. High-Level Architecture

AutoBe is an AI-driven backend generation system ("vibe coding") that transforms natural language requirements into fully functional, production-ready backend applications. It operates on a **Spiral Model**, moving through distinct phases of development: **Analyze -> Prisma -> Interface -> Test -> Realize**.

The system is a monorepo managed by `pnpm`, split into several packages with clear responsibilities:

- **`agent`**: The brain of the system. Orchestrates the AI (LLM) interactions, manages the development lifecycle, and maintains conversation state.
- **`compiler`**: The engine. A multi-tier compilation system that converts Abstract Syntax Trees (ASTs) generated by the agent into actual source code (Prisma schemas, TypeScript interfaces, NestJS controllers, etc.).
- **`interface`**: The contract. A shared library containing all type definitions, event structures, and protocol interfaces that bind the other packages together.
- **`rpc`**: The bridge. Exposes the internal `agent` API to the outside world (like the UI) using TGrid-based RPC over WebSockets.
- **`ui`**: The face. A React-based frontend that allows users to chat with the agent and visualize the generation process.
- **`filesystem`**: The storage. Abstracts file system operations, handling reading/writing of the generated project files.
- **`utils`**: The toolbox. Shared utility functions for common data manipulation tasks.
- **`benchmark`**: The judge. Tools to evaluate the performance and quality of the generated code.

## 2. Package Breakdown

### 2.1. `agent` (`packages/agent`)
This is the core business logic. It implements the `AutoBeAgent` class.
- **Responsibility**: Manages the conversation loop, interprets user intent, and drives the "vibe coding" process.
- **Key Components**:
  - `AutoBeAgent.ts`: The main entry point. Initializes `MicroAgentica` (the underlying agent framework) and manages the `AutoBeContext`.
  - `AutoBeContext`: Holds the state of the current session, including LLM models, token usage, and history.
  - `orchestrate/`: Contains the logic for different phases of development (Analyze, Prisma, Interface, etc.).
  - `prompts/`: A directory of Markdown files serving as system prompts for the LLM. These are compiled into TypeScript constants.
  - `factory/`: Helper functions to create agent instances and contexts.

**Workflow**:
1.  User sends a message via `conversate()`.
2.  `AutoBeAgent` processes this using `MicroAgentica`.
3.  The agent determines the current phase (e.g., `analyze`) and calls the appropriate internal controller.
4.  The controller uses the `compiler` to validate ASTs or generate code.
5.  Events (`AutoBeEvent`) are dispatched to notify listeners (e.g., the UI) of progress.

### 2.2. `compiler` (`packages/compiler`)
The deterministic code generator. Unlike the probabilistic nature of the Agent, the Compiler is strict.
- **Responsibility**: Takes structured data (ASTs) and produces valid, compiling code.
- **Key Components**:
  - `AutoBeCompiler.ts`: The main facade aggregating sub-compilers.
  - `prisma/`: Generates `schema.prisma` from an internal schema representation.
  - `interface/`: Generates TypeScript interfaces and DTOs.
  - `realize/`: Generates the actual implementation logic (API controllers, services).
  - `test/`: Generates test suites (E2E tests).
  - `typescript/`: Wraps the TypeScript compiler API to ensure generated code is syntactically correct.

**Strategy**: "Structure first, validate continuously, generate deterministically." The agent generates an AST, the compiler validates it. If valid, code is generated; if not, the error is fed back to the agent to fix.

### 2.3. `interface` (`packages/interface`)
The backbone of type safety.
- **Responsibility**: Stores all shared types.
- **Key Components**:
  - `events/`: Defines all event types (`AutoBeAnalyzeStartEvent`, `AutoBePrismaCompleteEvent`, etc.) used for real-time updates.
  - `facade/`: Interfaces for the Agent and Compiler (`IAutoBeAgent`, `IAutoBeCompiler`).
  - `histories/`: Types for storing conversation and state history (`AutoBeHistory`).
  - `prisma/`, `compiler/`: Types specific to those domains.

### 2.4. `rpc` (`packages/rpc`)
- **Responsibility**: Wraps `AutoBeAgent` in a `TGrid` service (`AutoBeRpcService`).
- **Mechanism**: Allows the `ui` (running in a browser) to call methods on the `agent` (running in Node.js) as if they were local functions.

### 2.5. `ui` (`packages/ui`)
- **Responsibility**: Provides the user interface.
- **Features**: Chat interface, file explorer for generated code, progress visualization for the different phases.

## 3. Core Concepts & Classes

### `AutoBeAgent` (in `agent/src/AutoBeAgent.ts`)
- **Extends**: `AutoBeAgentBase`
- **Implements**: `IAutoBeAgent`
- **Key Methods**:
  - `conversate(content)`: The main loop. Takes user input, runs the agent logic, and returns history.
  - `getFiles()`: Returns the current state of the generated project as a map of filenames to content.
  - `dispatch(event)`: Emits events to listeners.

### `AutoBeCompiler` (in `compiler/src/AutoBeCompiler.ts`)
- **Implements**: `IAutoBeCompiler`
- **Key Properties**:
  - `prisma`, `interface`, `typescript`, `test`, `realize`: Individual sub-compiler instances.
- **Key Methods**:
  - `getTemplate()`: Returns the base boilerplate code for the project depending on the current phase and database choice (Postgres/SQLite).

### `AutoBeHistory` (in `interface/src/histories/AutoBeHistory.ts`)
- A discriminated union of all possible history types (user messages, assistant messages, phase completions). This allow the agent to "remember" what happened in previous turns or sessions.

## 4. The "Vibe Coding" Workflow

1.  **Analyze Phase**: The agent discusses requirements with the user to build a conceptual model.
2.  **Prisma Phase**: The agent generates a `schema.prisma` file defining the data model. The `compiler` validates this schema against the Prisma engine.
3.  **Interface Phase**: The agent defines the API structure (endpoints, DTOs). The `compiler` generates TypeScript interfaces.
4.  **Test Phase**: The agent writes test cases. The `compiler` generates the test files.
5.  **Realize Phase**: The agent implements the logic to pass the tests. The `compiler` generates the final application code.

Throughout this process, the **Agent** provides the "creativity" (proposing changes), and the **Compiler** provides the "rigor" (ensuring code works).
